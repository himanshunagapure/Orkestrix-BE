# Gap Analysis: `aiobservabilitysrc` vs Workflow-Builder Runtime

**Date:** 24 August 2026  
**Purpose:** If `aiobservabilitysrc/` were meant to represent how our workflow-builder codebase actually runs workflows, what does it currently miss?

**Related docs:**

- Runtime architecture & plan: [`WORKFLOW_RUNTIME_OBSERVABILITY.md`](./WORKFLOW_RUNTIME_OBSERVABILITY.md)
- Design intent: [`AI_Observability_Technical_Design (4).docx`](./AI_Observability_Technical_Design%20(4).docx)

**Stance:** `aiobservabilitysrc` is a **reference** (capture → span → Mongo → optional eval). It is **not** a drop-in model of our FREEZE/DYNAMIC runtime.

---

## 1. What the demo actually is

`langgraph_demo.py` is a **single-process, linear document-extraction graph**:

```text
(optional transcribe) → classify → extract → evaluate fields against one source document
```

| Property | Demo |
|----------|------|
| LLM path | One LangChain `chat.invoke(...)` per node |
| Process | One Python process |
| Input | One document (`source_text`) |
| Storage | Local Mongo (`ai_observability`) |
| Tools | None |
| UI / human screens | None (optional `--interactive` only) |
| Tenancy | None |

All LLM calls are in-graph and visible to LangGraph/LangChain callbacks.

---

## 2. What our runtime actually is

```text
Build
  /scratch/preview     → phaseGraphs
  /plan/execute        → pr_*.py + gap tools + Angular screens
       ↓
Runtime
  main.py → Valkey → worker.py → executor.py
       ├─ FREEZE / DYNAMIC / MIXED graph.stream
       ├─ tool nodes → execute_dynamic_tool → gap-tool function_code
       └─ ui nodes   → interrupt() → browser
                          → POST /dynamic/execute/{project_id}  (agent sandbox)
                          → resume
```

| Property | Ours |
|----------|------|
| Graph | Generated at build time; loaded from `combined_file_path` |
| Tools | Generated by **gap tool generator**; may call LLM/HTTP/DB/email |
| Screens | Generated by **screen builder** (`/agent/generate-angular-app` etc.); backend functions may call LLM/APIs |
| Processes | **Worker** (graph + tools) + **Agent** (UI backends) + **Browser** |
| Identity | `execution_id`, `workflow_id`, `subscriber_id`, `org_id`, `project_id` |

---

## 3. Gap list (what the demo is missing)

### 3.1 Tool nodes + nested API/LLM calls inside tools

**Highest-priority product gap.**

| Demo | Ours |
|------|------|
| No tools | Nodes call `execute_dynamic_tool` → `LocalToolRegistry` → generated `function_code` |
| — | Code from **gap tool generator** (`backend/services/gap_tool_generator.py`) |
| — | Bodies use `google.generativeai` / `openai` / `anthropic` / `httpx` / Mongo / SMTP via `request_meta["credentials"]` |
| Callbacks see every LLM | Tool-body calls are **plain Python** → LangGraph callbacks **do not see them** |

**Missing in demo / package model:**

- `tool` spans  
- Nested `llm_tool` spans  
- Optional non-LLM side-effect spans (`http` / `db` / `email`) if “track API calls inside tools” is in scope  

---

### 3.2 UI screens + backend functions (other process)

**Same class of gap; different process.**

| Demo | Ours |
|------|------|
| No human UI | `interrupt({screen_id, ui_data, ...})` |
| — | Browser loads Angular app from **screen builder** |
| — | Screen functions → `POST /aiqod-agent/agent/dynamic/execute/{project_id}` |
| — | Sandbox exec on **agent** while **worker is paused** |
| — | Functions generated by **backend_generator**; may call LLM/APIs with credentials |

**Missing:**

- `ui` / `ui_function` / `llm_ui` spans  
- Cross-process correlation via `execution_id` in `request_meta`  
- Pause/resume as first-class parts of one trace  

---

### 3.3 FREEZE vs DYNAMIC vs MIXED

| Demo | Ours |
|------|------|
| Always an LLM pipeline | `GRAPH_TYPE`: **FREEZE** (no in-graph LLM), **DYNAMIC** (ReAct `_get_llm`), **MIXED** |
| Obs ≈ LLM node metrics | FREEZE obs is mostly **tools + UI**, not graph LLM |

**Missing:** Dual signal models; treating FREEZE as equal to DYNAMIC.

---

### 3.4 Multi-process runtime topology

| Demo | Ours |
|------|------|
| `python langgraph_demo.py` | `main.py` → Valkey `agentic_tasks` → `worker.py` → `executor.py` |
| Capture + eval in one process | Graph/tools on worker; UI backends on agent; live log via SSE |

**Missing:**

- Dual writers to one span store  
- Queue / SSE lifecycle  
- “Observation must never fail the run” under thread-pool workers  

---

### 3.5 Build vs runtime split

| Demo | Ours |
|------|------|
| Hand-written graph in the demo | `/scratch/preview` plans; `/plan/execute` emits artifacts |
| Obs wired beside the demo script | Obs must attach to **generated** `.py` / tools / screens without editing each artifact |

**Missing:** Executor-side (and `/dynamic/execute`-side) injection as the primary integration path.

---

### 3.6 Human-in-the-loop (product-shaped)

| Demo | Ours |
|------|------|
| Optional `--interactive` state edit | Real UI screens, assignment rules, multi-assignee loops |
| — | Resume payloads, `executed_by`, assignment re-pause **without** advancing LangGraph |

**Missing:** Structured `human_review`, interference/override rates tied to real pause/resume.

---

### 3.7 Multi-tenancy and run identity

| Demo | Ours |
|------|------|
| Single local DB | Every run has `execution_id`, `workflow_id`, `thread_id`, `subscriber_id`, `org_id`, `project_id` |
| — | Credentials injected into `request_meta` (must not be logged as secrets) |

**Missing:** Tenant-scoped spans and metrics; safe credential context.

---

### 3.8 “API calls” are broader than LLMs

Demo observability is **LLM-centric** (prompt / completion / tokens / cost / field eval).

Our tools and screens also perform:

- Mongo CRUD  
- Business HTTP APIs  
- SMTP / email  
- OCR, file I/O, etc.

If the goal includes “track API calls inside tools/screens,” the demo data model is incomplete. Spans need kinds such as:

```text
node | llm_graph | tool | llm_tool | ui | ui_function | llm_ui | human
(+ optional) http | db | email
```

---

### 3.9 Evaluation assumptions

| Demo | Ours |
|------|------|
| Schema / completeness / faithfulness vs one `source_text` | No default extract schema on nodes |
| Field accuracy as headline KPI | Many outputs are not field JSON; no gold labels |
| HF safety on extract completion | Optional later; wrong as default for every tool/UI call |

**Missing:** Contract-gated quality eval; **agent/reliability** metrics (latency, tokens, human override, step utility) as the default scorecard.

*(Their eval modules can still be reused later — see `WORKFLOW_RUNTIME_OBSERVABILITY.md` — once spans + contracts exist.)*

---

### 3.10 Graph topology complexity

| Demo | Ours |
|------|------|
| 2–3 linear nodes | Multi-phase graphs, subgraphs, bridges, DYNAMIC loops, tool fan-out |

**Missing:** Parent/child across subgraphs; loop detection / step utility; comparison to planned nodes in `phaseGraphs`.

---

### 3.11 Existing partial telemetry in our stack

We already have:

- `instances.state.execution_history`  
- Valkey `execution_stream:{execution_id}` (SSE)  
- `llm_token_count` (DYNAMIC/MIXED message scrape only)

The demo starts greenfield and does not model **joining or evolving** these surfaces.

## 4. Summary table

| # | Gap | Severity for our product |
|---|-----|---------------------------|
| 1 | Tool path + nested LLM/API inside gap tools | **Critical** |
| 2 | UI screen path + `/dynamic/execute` nested LLM/API | **Critical** |
| 3 | FREEZE / DYNAMIC / MIXED signal differences | **High** |
| 4 | Worker + agent + browser topology | **High** |
| 5 | Executor injection (don’t own generated graph) | **High** |
| 6 | Real interrupt / resume / assignment | **High** |
| 7 | Tenant / workflow / project identity | **High** |
| 8 | Non-LLM API/DB/email tracking (if in scope) | **Medium–High** |
| 9 | Extraction-style eval as default | **Medium** (wrong default; ok as opt-in) |
| 10 | Multi-phase / loop topology | **Medium** |
| 11 | Bridge to existing history / tokens / SSE | **Medium** |

## 5. What the demo *does* still teach us (keep)

These ideas remain useful as reference — reimplement under `langgraph/` (+ agent hooks), do not assume drop-in:

| Idea | From |
|------|------|
| Trace / span mental model | `models.py`, design doc |
| LangGraph callbacks for **in-graph** LLM nodes | `langgraph_hooks.py` |
| Async non-blocking writes | `sinks.AsyncWriter` |
| Mongo upsert + indexes | `export.MongoStore` |
| Eval never raises; absent ≠ zero | `evaluation.py` / `metrics.py` |
| Build order: capture → storage → evaluation → reporting | Design doc |

---

## 6. Bottom line

`aiobservabilitysrc` is a good reference for:

> “Callback → span → Mongo → optional eval” on a **LangChain LLM inside one simple graph**.

It does **not** represent our product’s core shape:

> **Generated FREEZE/DYNAMIC workflows** that call **generated tools and screens**, which themselves call **LLMs and other APIs**, across **worker + agent**, with **human pause/resume** and **multi-tenant** identity.

The largest missing pieces — as you noted — are **nested calls inside gap tools and screen backend functions**. Close behind: **multi-process UI execution**, **FREEZE without in-graph LLM**, **human-in-the-loop**, and (if required) **broader API/DB tracking**, not only LLM completions.

For how we plan to cover those gaps in our codebase, see [`WORKFLOW_RUNTIME_OBSERVABILITY.md`](./WORKFLOW_RUNTIME_OBSERVABILITY.md).
